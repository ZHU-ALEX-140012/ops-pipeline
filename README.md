# ops-pipeline

个人质量保障与运维流水线：**确定性脚本负责采集，AI 负责判断，脚本再决定要不要打扰你。**

用 DeepSeek Harness 的 `headless` 模式做判断层，用 Windows 任务计划程序做触发，
用 SQLite 存历史，用企业微信发告警。**零第三方依赖**，只用 Python 标准库。

> **项目位置**：正本在 `D:\AITool\ops-pipeline`。桌面上的 `ops-pipeline` 是指向这里的
> **快捷方式**，不是第二份拷贝 —— 刻意只保留一份，避免两份代码各自演化后分叉。

---

## 为什么不用 cron + 一个脚本

cron 能做到"每天早上 8 点跑脚本"。但它做不到这些：

- 7 个接口用例挂了 3 个 —— **是同一个根因还是三个独立回归？**
- 日志里冒出一个以前没见过的错误簇 —— **是新问题，还是已知噪声？**
- 昨天同一时间也挂过一次 —— **这是偶发还是趋势？**
- 结论要写成人能读的报告 —— **哪句是事实、哪句是推测？**

这四件事需要判断。**这才是这套东西存在的理由**：cron 管"什么时候跑"，AI 管"跑出来的东西意味着什么"。

## 四条流水线

| 任务 | 频率 | 干什么 | 判断层要回答的问题 |
|---|---|---|---|
| `api_watch` | 每小时 | 探测外部接口的健康与延迟，与 30 天基线比对 | 这次失败是上游故障、结构变更，还是网络抖动？ |
| `regression` | 每天 08:30 | 对自己的接口跑 7 条契约用例（自带靶子服务） | 这几个失败是同一个根因，还是几个独立回归？ |
| `log_scan` | 每天 09:00 | 把日志聚成模板，比对两个窗口的量级 | 哪个错误簇是**新出现**的、哪个**量级炸了**，同源吗？ |
| `daily_report` | 每天 09:30 | 汇总 24h 的运行/告警/token，写一份日报 | 这一天的整体情况怎么样，有什么该关注的？ |
| `heartbeat` | 每天 23:00 | 用**独立机制**检查"预期该跑的 run 有没有跑" | （不用 AI：判据是确定的时间差） |

## 架构

```
┌─ 触发层 ──────────────────────────────────────────────┐
│  Windows 任务计划程序                                  │
│   每小时    → api_watch    接口可用性巡检              │
│   每天 08:30 → regression  接口回归 + 归因 + 晨报       │
│   每天 09:00 → log_scan    日志模板聚类 + 归因 + 简报    │
│   每天 09:30 → daily_report 汇总日报（固定会话，有记忆）  │
│   每天 23:00 → heartbeat   检查"预期该跑的跑了没"       │
└─────────────────────┬────────────────────────────────┘
                      │  python -m ops --task X --once
┌─ 执行层（确定性 Python，绝不调用 LLM）───────────────┐
│  采集/跑用例 → 落库 → 基线比对 → 规则判定 → run.json   │
└─────────────────────┬────────────────────────────────┘
                      │  run.json（文件契约）
┌─ 判断层（dsh --profile headless）───────────────────┐
│  读事实 → 归因 → 分级 → 写 verdict.json + 报告         │
└─────────────────────┬────────────────────────────────┘
                      │  verdict.json（文件契约）
┌─ 裁决与告警层（core/pipeline.py，所有任务共用）─────┐
│  读结论 → 去重/冷却/静默 → 发企业微信 → 落库 → 报告     │
└───────────────────────────────────────────────────────┘
```

### 三条铁律

1. **确定性的活给脚本，判断性的活给 AI。**
   网络请求、断言、算分位数、失败分组是脚本的活；归因、分级、写报告是 AI 的活。
   反过来做（让 AI 每次重新生成测试/爬虫代码）会得到不稳定、难复现、还烧 token 的系统。

2. **AI 只能读写文件契约，不能直接发告警。**
   AI 产出 `verdict.json`，由脚本决定发不发。于是告警逻辑可测试、可审计、可限流，
   **AI 的幻觉不会直接炸你的微信**。同时也解决了无人值守的权限问题：
   判断层不碰网络和数据库，就不存在"需要人批准的操作用户不在场"导致任务失败。

3. **执行层不依赖 AI 就能跑通。**
   把 `ai.enabled` 关掉，整套流水线照常工作，只是结论标注为"规则层兜底、未经 AI 分析"。

### 第四条（实现时加的）：收尾逻辑只有一份

判定 → 报告 → 裁决 → 告警 → 落库 这段逻辑在 `core/pipeline.py` 里，
三条流水线共用。**复制一份的代价**是：冷却规则、降级标注、幂等键会在两边各自演化，
最后出现"这条流水线的告警被抑制、那条没有"的不一致 —— 那种 bug 极难发现。

```powershell

scripts\set-secret.cmd -Name OPS_MAIL_TO   -Hint "收件地址（可以就是同一个邮箱）"

#    其它通道（按实测结论排序，详见 DESIGN.md 附录 E6）：
#      ntfy       服务可达，但国内安卓应用商店不让装
#      wecom      群机器人：需要普通内部群，全员群/单人企业拿不到入口
#      wecom_app  自建应用：需已备案域名或公网服务器才能填企业可信IP
#      pushplus   实测要求付费实名认证（code=905）

# 5) 注册计划任务（双击 scripts\register_tasks.cmd 也行）
scripts\register_tasks.cmd -DryRun            # 先预览
scripts\register_tasks.cmd                    # 注册 api_watch / regression / heartbeat
#   log_scan 默认不注册：它监视的日志源还指向演示用的合成日志。
```

第 2 步不是可选项：**你必须先证明"监控能抓到已知故障"，才敢相信它在真实故障面前不撒谎。**

### 常用开关

```powershell
python -m ops --list                                   # 列出任务
python -m ops --task regression --once --dry-run       # 不发真告警，落本地日志
python -m ops --task regression --once --no-ai         # 强制规则层兜底
python -m ops --task regression --once --override regression.variant=v1
```

`--override KEY=VALUE` 是为"临时改个参数重跑一次"准备的，不用为了跑一次去改配置文件。

### 企业微信自建应用：三个值到底在哪拿

**关键区别：这三个值不在「企业微信」客户端里，而在「管理后台」网页上。**
客户端是聊天用的；管理后台是另一个地方：

* 浏览器打开 <https://work.weixin.qq.com/> → 点「管理后台」→ 用手机企业微信扫码登录
* 或者：桌面客户端**左上角头像 → 管理企业**，会跳转到同一个后台

登录后按顺序做四件事：

| 步骤 | 位置 | 拿到什么 |
|---|---|---|
| 1 | 顶部「我的企业」→ 左侧「企业信息」→ 拉到**页面最下方** | **企业ID**（形如 `ww1234567890abcdef`）= CorpID |
| 2 | 顶部「应用管理」→「应用」→「自建」→ **创建应用** | 上传任意图标、填个名字（如 `ops-alert`） |
| 3 | 创建时的「可见范围」 | ⚠️ 必须选**你自己**（或整个企业），否则推送会返回 `invaliduser` |
| 4 | 创建后自动进入的**应用详情页** | 直接看到 **AgentId**（纯数字，形如 `1000002`）；**Secret** 点「查看」→ 会发一条消息到企业微信里，点开就能看到 |

四步做完后回到终端：

```powershell
scripts\set-wecom-app.cmd
```

脚本会依次问你这三个值，写入 `config\secrets.local.toml`，然后**立刻发一条测试消息**。

**拿不准某一步时**：`scripts\set-wecom-app.cmd -Show` 看当前配到哪了（值会打码）；
报错里带 `errcode` 时按码查 <https://open.work.weixin.qq.com/devtool/query>。

## 关键设计决策

| 决策 | 选择 | 理由 |
|---|---|---|
| 触发方式 | Windows 任务计划程序调 `--once` | 无状态、可重入、可手动补跑；不需要守护进程 |
| 依赖 | **零第三方依赖**（仅标准库） | 无人值守场景下依赖越少越不容易半夜挂掉 |
| 配置格式 | TOML（`tomllib`，Python 3.11+ 自带） | 要有注释，又不想引入 PyYAML |
| AI 凭据 | `--patch` 切到 `deepseek-account` | 复用桌面端登录，**不用额外申请 API Key** |
| AI 会话 | 巡检用新会话；日报用固定会话 | 每小时一次独立检查共用会话会让上下文无限增长 |
| 用例形式 | 声明式数据 + 断言 DSL | 加用例不用碰运行器；失败明细天然结构化，AI 归因不用解析文本 |
| 回归靶子 | 自带 v1/v2 变体，任务自己拉起又关掉 | 你无法在真实项目里故意弄坏接口；计划任务也不该依赖"你得先手动启动服务" |
| 告警幂等 | 唯一索引 `(dedup_key, run_id)` | 单轮幂等 + 跨轮冷却。若只按 `dedup_key` 唯一，同一条告警永远发不出第二次 |
| dry-run | 计入冷却 | dry-run 必须**忠实模拟**真实发送，否则演练结果误导人 |
| 发送失败 | 不计入冷却 | 失败就该下一轮重试，不能被冷却压住 |
| 连续失败 | **限定 24 小时窗口** | 不设窗口会和 `failures_24h` 自相矛盾（详见下文） |
| 日志基线 | 同一文件里比**两个紧邻窗口**（当前 vs 前一窗口） | 第一轮就有基线，不存在冷启动空转；历史库只作补充 |
| 日志基线污染 | `log_window.anomalous` 标记，**故障期窗口不进基线** | 否则故障量级被算成基线，异常逐渐变成"新常态" |
| "新模板"判据 | 看 `first_seen` **是否在宽限期内**，而非"历史里有没有" | 否则第二轮就成老模板，首轮告警被静默/冷却后就永远静默 |
| 存储 | SQLite + WAL，时间一律 UTC | 单机足够；原始 `run.json` 同时落盘，DB 坏了也不丢证据 |
| 报告目录 | 按**本地**日期 | 存储用 UTC，但人是按本地日期翻报告的 |

## 失败与降级

监控系统最大的敌人不是采不到数据，而是**静默失败** —— 程序正常退出、你以为"今天没异常"、实际一周没采到数据。

| 故障 | 表面现象 | 防护 | 是否实测 |
|---|---|---|---|
| 脚本崩溃 | 无 run 记录 | **心跳任务**用独立机制检查"预期 run 是否缺失" | ✅ |
| 采到 0 条 | "一切正常" | **0 条 = 失败**，显式判空并告警 | ✅ |
| AI 超时/报错/路径错 | 无 verdict | **降级**为规则层判定，结论标注"未经 AI 分析"，告警照发 | ✅ |
| AI 超预算 | 无 verdict | `max_calls_per_day` 闸门 → 转降级模式 | 代码就绪 |
| AI 幻觉乱报 | 告警轰炸 | AI 只产 verdict；脚本裁决；`confidence` 阈值 | 设计保证 |
| AI 漏报 | 无声 | 规则层设**兜底硬阈值**，不依赖 AI 也能触发 | ✅ |
| 告警通道挂 | 无人知道 | 落本地日志 + 发送失败不计冷却 → 下一轮重试 | ✅ |
| 计划任务没触发 | 全静默 | 心跳用**不同机制**实现 | ✅ |
| DB 写失败 | 数据丢失 | WAL + 原始 `run.json` 落盘兜底 | 设计保证 |
| 报错但看不懂 | 排查成本高 | `diagnose()` 把 dsh 原始报错翻译成"人话 + 怎么办"，并打到 stdout | ✅ |

## AI 判断层实测：它抓到了我自己写的 bug

这是最值得看的一段。第一次真实运行 AI 判断层时，它给出的证据里包含这样一条：

> `baseline.samples=1` 却记 `consecutive_failures=5`，而 `failures_24h=1`——
> 24 小时内仅 1 次失败却存在连续 5 次失败，时间跨度无法判断。
> **该不一致会削弱规则层触发条件的可信度。**

它是对的。`consecutive_failures` 当初**没有时间窗口**：昨天 17:05 的失败被算进了今天的"连续失败"，
而 `failures_24h` 有时间窗口 —— 两个指标自相矛盾。修复后：

- `failure_streak()` 限定 24 小时窗口，两个指标重新自洽；
- 额外输出 `streak_span_minutes`，因为"连续 5 次"可能是 5 分钟也可能是 5 天；
- 提示词里补齐了每个字段的**精确语义**，并明确要求"字段矛盾时先确认是不是时间窗口不同"。

修好之后，AI 的结论变成了：
> `consecutive_failures=2, streak_span_minutes=1.5, failures_24h=2` —— **两个窗口在本轮互相自洽**

**这件事本身就是这套架构的价值证明**：一个只会打印指标的系统不会告诉你指标之间矛盾。

### AI 归因的另一次实测（回归流水线）

对 3 个注入的回归，AI 的结论是：

> **3 个接口出现独立回归：2 处契约变更 + 1 处 404 语义缺失**
> ……同目录下的 `/api/users/9999` 同样场景返回了正确 404，
> 说明这**不是全局约定变更**，而是该接口自身缺失未找到分支。

最后那句交叉推理没有写在提示词里 —— 它是从"4 个通过的用例里包含 `user_not_found_status`"
自己推出来的。这正是"机器数数 + AI 判断"分工想要的效果。

### 日志分析流水线：又抓到两个（第 3 周）

**第一个**：AI 指出 `consecutive_failures` 与 `failures_24h` 用不同时间窗口（上一节的 bug），
这次它指向了基线设计本身：

> "39.3 倍'突增'更可能是上一窗口 220 次异常偏低造成的对比假象"
> "`history_avg`/`history_median` 均为 379 且 `history_windows=5`，与'历史从未出现'矛盾"

两条都指向同一个根因：**我把"故障期"的窗口写进了基线**。于是规则层和 AI 看到互相矛盾的信号，
而更严重的是——第 2 轮之后故障被"正常化"，`status=ok`，悄无声息。

修法两条，都是原则性的：

1. **基线只能由正常期构成**：`log_window.anomalous` 标记被判定为异常的窗口，排除在基线之外；
   参照值优先取"同文件的前一窗口"（固定不变的"之前"），只有它没有该模板时才退到历史**中位数**。
2. **"新"要用时间判据**：看 `first_seen` 是否在宽限期内（默认 3 天），
   而不是"历史窗口里有没有记录"。

修完之后的实测对比：

| 轮次 | 修复前 | 修复后 |
|---|---|---|
| 第 1 轮 | 检出 → 告警 | 检出 → 告警发出 |
| 第 2、3 轮 | `status=ok` **静默** | `severity=alert` **仍检出**，由**冷却**抑制重复 |

区别在于：持续故障由冷却机制管住噪声，而不是被误判成"新常态"。

## 目录结构

```
ops-pipeline/
├─ DESIGN.md              设计方案（含"实现与设计的偏差"附录）
├─ config/
│  ├─ config.toml         唯一需要你改的文件
│  ├─ dsh-headless.patch.yml  复用桌面账号登录；凭据仍从真实 ~/.dsh 读取
│  ├─ config.smoke.toml          冒烟测试：只打本地靶子、不走 AI
│  ├─ config.ai-test.toml        AI 判断层验证
│  └─ config.ai-degraded.toml    降级路径验证（故意写错 ai.cmd）
│     secrets.local.toml         本地密钥（凭据文件，已在 .gitignore 中；由 set-webhook.cmd 生成）
├─ ops/
│  ├─ __main__.py         入口：python -m ops --task X --once [--override ...]
│  ├─ core/
│  │  ├─ config.py        配置与凭据（凭据只从环境变量读）+ --override
│  │  ├─ http.py          探测与通用 JSON 请求（超时/重试/限速）
│  │  ├─ checks.py        接口契约断言 DSL（纯函数，独立单测）
│  │  ├─ logparse.py      日志模板提取 Drain 算法（纯 Python，独立单测）
```

## 告警邮件长什么样

**只讲人话** —— 这条是收件人反馈后改的：

```
🔴 严重　日志已停写超过24小时，服务很可能已经停了

这个应用已经一天多没有产生任何新日志，最后一条日志停在约24小时前，
本轮窗口里一条记录都没有。在停写之前的那个窗口，数据库连接失败和缓存
因内存不足清理失败的报错明显增多。现在看不到任何新日志，所以"没有报错"
并不等于正常。

**这意味着**：服务很可能已经停止运行，或者日志采集/轮转出了问题，
这段时间内的故障完全不可见，用户请求可能已经在失败。

**建议**：请先确认这个应用的进程是否还在运行、日志文件是否被轮转或采集
路径是否失效，然后再检查它的数据库连接和缓存内存情况。

———
日志源 0/1 正常，失败 1
完整报告：D:\AITool\ops-pipeline\data\reports\...\log_scan-....md
```

判断层通过 `plain_summary` / `impact` / `suggested_action` 产出这三块；
技术细节（`evidence`）**只进报告文件，不进邮件**。改之前是把 evidence 原样贴进邮件，
结果是满屏 `samples:` / `baseline.worldtime:` / `modal_body_hash`，收件人看到的是一堵墙。

邮件里不许出现 `samples:` / `baseline.` / `p95` / `status_code`。

## 判断层评测（eval）

前几节都在说"怎么做对"。这一节回答一个更难的问题：**你怎么知道这套判断真的有效？**

答案不能是"我跑了一次，看着不错"——那是叙事，不是证据。所以有一个黄金集评测脚手架：

```bash
python tools/eval_suite.py --rule-only     # 规则层基线：免费、秒级
python tools/eval_suite.py --limit 5       # 小样本试探（控成本）
python tools/eval_suite.py --only log_scan # 按任务筛
python tools/eval_suite.py                 # 全量（真实调用判断层）
python tools/eval_suite.py --repeat 5      # 重复跑，量化不稳定性
python tools/eval_suite.py --compare       # 与上次对比 → 回归检测
```

**关键设计：同时跑「规则层」和「AI」两臂。**
只报 AI 的绝对分数没有意义——"准确率 85% 是好是坏？"只有在知道规则层也有 84%
（那这层 AI 白加了）或只有 60%（那 AI 很值）之后才能回答。

### 黄金集：24 个场景，9 个是反向用例

| 任务 | 场景数 | 覆盖 |
|---|---|---|
| api_watch | 7 | 全正常 / 单目标失败 / 全部失败 / 轻微延迟 / 严重延迟 / 冷启动 / 结构性变更 |
| regression | 4 | 全通过 / 单条失败 / 同源聚类失败 / 混合独立失败 |
| log_scan | 6 | 平稳 / 新错误模板 / 量级激增 / 日志停写 / 解析失败 / **新 INFO 模板（规则层误报）** |
| heartbeat | 2 | 全部按时 / 有任务超期 |
| price_watch | 5 | 平稳 / **到价** / **一个价都没抓到** / **冷启动被误判新低** / 异常上涨 |

**反向用例占 9/24**，因为告警系统死于误报——只有正向题的黄金集，
一个永远返回 `alert` 的模型能拿满分（这是评测最常见也最致命的缺陷）。
`test_has_both_positive_and_negative_cases` 把它变成硬约束。

price_watch 的三个场景都是"规则层会报、判断层该驳回或该改口气"的类型，
其中 `pw_04_cold_start_false_new_low` 和 `ls_06` 是同一类题：
**规则层给出的线索会原样出现在喂给模型的输入里，而正确答案是驳回它。**

> ⚠️ 下面「实测结果」与「配对实测」两节里的数字，都是在**价格场景加入之前**
> （19 个场景、判断层覆盖 17 个）测的，不要与现在的 24 个混着看。

### 指标口径

* **`should_alert` 混淆矩阵** → 精确率 / 召回率 / F1 / 准确率。
  两者都报，但强调**精确率**：召回率低的后果是漏报，精确率低的后果是**用户把告警关掉**。
* **分母为 0 时返回 `n/a` 而不是 100%**——没有正预测时精确率是未定义的，报满分会骗人。
* **`root_accuracy` 是关键词命中率**，不是语义评分。局限写在报告里，不假装它是准确率。
* **token 与耗时一并采集**："更准"必须带上"多贵"，否则结论没有决策价值。

### 实测结果

同一批冻结夹具，**跑了两次全量**（这不是浪费——第二次暴露了第一次看不见的问题）：

| 指标 | 规则层<br>（同子集 n=17） | AI 第 1 次 | AI 第 2 次 |
|---|---|---|---|
| `should_alert` 精确率 | 91.7% | **100.0%** | 91.7% |
| `should_alert` 召回率 | 100.0% | 100.0% | 100.0% |
| `should_alert` F1 | 95.7% | 100.0% | 95.7% |
| 严重级别准确率 | 100.0% | 100.0% | 100.0% |
| **根因关键词命中率** | **64.3%** | **100.0%** | **100.0%** |

规则层在这 19 个场景上是 精确率 92.3% / 召回率 100% / 根因命中 66.7%。
成本：平均 **21.0 秒/次**，输入约 6.6k tokens、输出约 3.5k、cache 读约 68k。

**怎么读这张表（这才是重点）：**

1. **唯一在两次运行中都稳定提升的指标是「根因命中率」：64.3% → 100%。**
   这正是判断层该做的事——规则层能**发现**异常（召回率 100%），
   但说不清"这意味着什么、该做什么"。
2. **`should_alert` 上 AI 的优势不可复现**（100% → 91.7%）。
   差异全部来自同一个场景的翻转，所以**不能声称"AI 让误报率降到 0"**。
3. 两次运行唯一的分歧是 `ls_06`（规则层误报、正确答案不告警）：
   第 1 次答对，第 2 次答错且**置信度只有 0.55**——它自己的推理写着"无影响"、
   "不是故障"，却把动作标记设成了告警。**推理与动作不一致**。
4. 单独把这道题重复跑 5 次：**5/5 全部答对**。但在两次全量里错了 1 次。
   所以差异可能来自批次上下文，也可能只是采样波动——
   **当前样本量不足以区分这两种解释**。

> **结论**：单次跑分不能作为结论。要看趋势就得重复跑、看均值与稳定性。
> 这个认识只有在建了评测脚手架之后才可能出现——在那之前，
> 所有"AI 抓到了真问题"的说法都来自个案观察，无法区分"它行"和"它这次碰巧行"。

### 三个来自评测设计本身的发现

1. **`run@1` 契约并非各任务统一**：`log_scan` 的 `targets/ok/failed` 按**日志源**计，
   而 `samples` 按**日志模板**计。写一致性校验器的第一版就直接把 log_scan 判成
   "自相矛盾"——这个不一致在 225 个单元测试里一直没暴露，因为它只在
   "有人试图统一描述它"的时候才会现形。现在有专门的单测锁住它。
2. **评测必须尊重"哪些任务真的用 AI"**：`heartbeat` 生产上是纯规则的（判据是确定的时间差），
   第一版无脑给每个任务都调用判断层，直接因为缺 `heartbeat.md` 崩了。
3. **对照臂必须在同一子集上比较**：AI 只覆盖 17/19 个场景（当时的价格场景还没加），
   如果拿下沉到不同 n 的规则层分数去比，差值是假的。现在报告里同时给
   "规则层（全部 19）"和"规则层（与 AI 同子集 17）"两个数。

### 已知局限（写在报告里，不藏着）

1. 关键词评分 ≠ 语义评分，真正的根因质量需要 LLM-as-judge 或人工标注
2. 场景数还很少（写这段时 19 个，含价格场景后 24 个），单个翻转就会让百分比
   跳动 4~5pp，不要拿小数点后的差异当结论
3. "规则层误报、正确答案是驳回"这类型题现在有 2 个（`ls_06` 与 `pw_04`），
   但相对 24 个场景仍然偏少 —— 它恰好是最能体现判断层价值、也最不稳定的题型
4. 夹具是**冻结的 JSON**（`evals/golden/`），改题目要显式改 `evals/fixtures.py`
   再 `python -m evals.build`——这样分数变化才只反映模型/提示词的变化

**知道并写出自己评测的局限，比报一个漂亮的分数更接近工程。**

## 判断层可以主动查证（只读调查工具）

判断层不只是"读一段 JSON 然后回答"——它还能**主动去查证**。四个工具：

| 工具 | 能碰什么 | 边界控制 |
|---|---|---|
| `read_log` | 按 `[[log_scan.sources]]` 里的**名字**读日志尾部 | 不接受路径 → 没有路径穿越；**有界尾读**（实测 11MB 日志 0.02 秒）；输出截断 |
| `query_history` | 以**只读**方式查历史运行与告警 | `mode=ro`，不可用则退到 `PRAGMA query_only`（写入同样被 SQLite 拒绝）；连接与语句都有超时 |
| `probe_target` | 按 `[[api_watch.targets]]` 里的**名字**重新探测 | 不接受 URL/主机名 → 不能拿这台机器当跳板扫内网；探测自带超时 |
| `read_report` | 读 `data/reports` 下某次运行的报告 | 校验 run_id 形状 + 路径必须落在报告目录内 |

> **关于"超时"**：这里没有用外部看门狗，而是让**每个操作本身有界** ——
> 文件读有字节上限、网络探测有超时、数据库连接和语句有超时。
> 这比"跑起来再掐"更可靠：Python 杀不掉卡住的线程，而"有界"从构造上就不会卡住。
> 另外每一次工具调用外面还有 harness 自己的 tool-call 超时兜底。

```bash
python tools/investigate.py catalog          # 看允许访问什么、还剩几次预算
python tools/investigate.py read-log --source app --tail 300 --pattern "ERROR"
python tools/investigate.py history  --task api_watch --days 7
python tools/investigate.py probe    --target worldtime
python tools/investigate.py report   --run-id <run_id>
```

**为什么是"白名单 + 只读"，而不是"给它文件系统权限"**：判断层本来就有
`fs` / `fs-search` / `pwsh` / `web` 工具（`dsh --profile headless --dump-config` 里能看到），
提示词里写的"不要读日志文件"**只是建议，不是安全边界**。
这组工具的价值不在于加权限，而在于**把读操作收窄到配置里已声明过的对象上**，
并且每次运行有预算、每次都留审计痕迹。它们是纯读的，
所以判断层即使被提示注入操纵也改不了任何东西 —— 而它自带的 `pwsh` 可以。

### 实测：一次真实的七步调查

给判断层这批工具后，它在一次真实巡检里自己走完了这条链：

```
catalog                                   → 拿到允许访问的对象
history --task api_watch --days 7         → 查这个目标过去有没有成功过
probe --target worldtime                  → 立刻重探，确认"现在仍然失败"
read-log --pattern "worldtime|URLError"   → 去日志里找对应报错
report --run-id <历史 run>                → 读上次同类问题的结论
write verdict → 自己用 shell 校验 JSON → 发现格式错 → edit 修好 → 复验
```

**最后那步尤其说明问题**：它自己写了 JSON、自己校验、发现不合法、自己修好、再验一次 ——
这不是"一次问答"，而是一个带反馈闭环的循环。

### MCP 服务端：实现了，但今天挂不上去（诚实说明）

`ops/investigate/mcp.py` 是一个**纯标准库手写的 MCP 服务端**（JSON-RPC 2.0 over stdio，
实现 `initialize` / `tools/list` / `tools/call` / `ping` / 通知），协议完整性由
一个真的 stdio 测试客户端验证。它和 CLI **共用 `ops/investigate/tools.py` 这一份实现**，
不存在两条通道各自演化的问题。

**但 `dsh headless` 的 profile 里没有 MCP 客户端的配置面** ——
我用 `dsh --profile headless --dump-config` 逐项查过，只有一个
`dsh-mcp-resources`（MCP *资源*，不是服务器连接）。MCP 服务器是通过 ACP 的
`session/new` 由**客户端**传 `mcpServers` 挂上的（asar 里能看到
`SessionBuilder.withMcpServer`），而 `dsh headless` 自己就是那个客户端，命令行没暴露这个入口。

所以现状是：**MCP 服务端可用、可测试、可被任何 MCP 客户端使用；
流水线今天实际走的是同源的 CLI。** 两者边界控制完全一致。

### 预算：把"拦得住"和"看得见"分开

工具调用预算是 **6 次/运行**。但这里有一个实测出来的重要区分：

| 角色 | 谁来做 | 在什么环境下有效 |
|---|---|---|
| **强制**（拦住第 7 次） | CLI 写状态计数器 | 需要状态目录**可写** |
| **检测**（看得见超了） | 宿主侧从 `events.ndjson` 数 `tool_call` | **任何环境都有效**，不需要写入 |

为什么必须分开：实测环境里**判断层的沙箱 shell 只能读、状态文件写不进去**
（`SetNamedSecurityInfoW ... grantWrite(D:\AITool\ops-pipeline)`），
于是 CLI 的计数器落不了盘。第一版还把写入异常 `except OSError: pass` 吞掉了，
结果判断层连调 5 次工具、每次预算行都显示"已用 0/6" —— **硬上限形同虚设，而日志里毫无提示**。

现在三件事都做了：

1. 写入失败**显式报告**（stderr 明说"本轮工具预算未生效"）；
2. `catalog` 自带**落盘自检**，直接告诉你计数能不能写、当前运行标识是什么；
3. 宿主侧从事件流**独立计数**并写进报告附注 —— 即使拦不住也一定看得见。

> **"拦得住"和"看得见"混为一谈，是这类护栏最常见的自欺。**

## 人工反馈回路：让"它在你这儿准不准"变成数据

离线黄金集能回答"模型在 **24 个场景**上多准"，回答不了"**它在你这儿多准**"。
真实环境里的误报往往长得跟黄金集里的不一样 —— 只有收到邮件的人知道。

**怎么反馈**：收到告警邮件后**直接回复**，正文写「对」或「错」即可。系统靠主题里的
`#<标记>` 认领是哪一条，下一轮 `feedback_scan` 就会记上。

```bash
python tools/feedback.py list     # 看最近的反馈
python tools/feedback.py stats    # 汇总人工标注准确率
python tools/feedback.py record --run-id <id> --vote down --note "其实是预期内的"
python tools/feedback.py scan     # 立即去邮箱收一次回复
```

日报里会带一段人工反馈汇总，判错的那几条会被特别点出来。

### 为什么是"回复邮件"而不是"点邮件里的链接"

最自然的交互是邮件里放两个按钮。但那需要一个**从手机可达的地址** ——
家宽既没有公网 IP 也没有域名，链接点下去只会打到手机上。
这和当初企业微信回调 URL 撞的是**同一堵墙**。

回复邮件不需要任何可达地址：邮件出去、回复回来，中间不需要你的机器能被访问。

### 三个刻意的设计取舍

| 决策 | 选择 | 理由 |
|---|---|---|
| 覆盖 vs 追加 | 同一来源对同一轮**以最后一次为准**（UPSERT） | 人改主意是正常的，累计两次会把统计弄脏 |
| 认不出来怎么办 | **静默跳过**，不算错误 | 自动回复、签名、无关邮件都是常态；猜错比不认更糟 |
| 关键词判定顺序 | **先判负向** | `"不对"` 里含 `"对"` —— 先判正向会把误报记成判对，准确率虚高 |

最后一条有专门的单测盯着（`test_down_checked_before_up`）。**把误报记成"判对了"，
比没有反馈更糟** —— 它会让准确率虚高，正好掩盖真问题。

### ⚠️ 这个准确率天生有偏

你更可能去反馈**判错**的那几条。所以 `stats` 打印的是"人工标注准确率"，
只能看趋势、找反例，**不能当成模型在全部告警上的准确率**。
输出和日报里都明写着这句话 —— 一个不说明采样偏差的准确率是误导。

它的真正用途是**收集反例**：判错的那几条拿去补进黄金集，下一轮离线评测就有了新题型。

### 配对实测：加了只读工具，**这次没有变准**

同一批冻结夹具、同一次运行里跑两臂（当时的 19 个场景，判断层覆盖 17 个；
**价格场景是后来加的，没有重跑这一节**）：

| 指标 | 规则层 (n=17) | AI 无工具 | AI + 只读工具 | 有工具 − 无工具 |
|---|---|---|---|---|
| `should_alert` 精确率 | 91.7% | **100.0%** | **100.0%** | 0.0 pp |
| `should_alert` 召回率 | 100.0% | 90.9% | 90.9% | 0.0 pp |
| `should_alert` 准确率 | 94.1% | 94.1% | 94.1% | 0.0 pp |
| 严重级别准确率 | 100.0% | 100.0% | 100.0% | 0.0 pp |
| 根因关键词命中率 | 64.3% | 92.9% | **100.0%** | +7.1 pp |
| 输入 tokens | — | 152,882 | **125,671** | −18% |
| cache 读 tokens | — | 1,547,264 | **1,049,344** | −32% |
| 平均耗时 | — | 33.9s | **27.8s** | −18% |

**这是一次"零结果"，我照实报。**

- **决策指标完全一致**：两臂各错 1 个场景，抵消了。
- **成本反而更低**（少 18% 输入、快 18%）。**但只有一次运行，不能当结论** ——
  上一节刚证明同一批输入重复跑分数会抖，单次差 18% 完全可能是噪声。
- 唯一正向的信号是根因命中率 92.9% → 100%，而那是**一个场景的翻转**（n=14，1 个 = 7pp）。

### 为什么没测出好处：**题目本身不需要调查**

这才是这次配对实验最有价值的产出。翻回去看逐个场景：

| 场景 | 有工具臂调用工具 |
|---|---|
| aw_01 / aw_04 / aw_06 / ls_01 / rg_01–04 | **0 次** |
| aw_02 | 2 次 · aw_07 | 2 次 · aw_03/05 | 3–4 次 |
| ls_02–ls_05 | 3–4 次 · **ls_06** | **6 次（用满预算）** |

模型**只在能改变结论时才查**（异常在场就查、输入已足够就跳过）—— 这个行为本身是对的。

但问题在于：**19 个夹具全都是"自证"的** —— `run_doc` 里 `samples`/`baseline`/`anomalies`
一应俱全，答案全在输入里。**没有一道题必须去查日志或历史才能答对。**
既然如此，工具当然测不出价值。

> **评测只能衡量它的题目所要求的能力。** 想衡量"调查能力"，就得有
> "证据不足、必须自己去查"的题目 —— 而那正是黄金集现在缺的一类。

### 顺带发现：两个"错"其实是我的标签太严

两臂各错的那一个，**都不是推理错误**：

| 场景 | 模型说了什么 | 我的标签 |
|---|---|---|
| `aw_05` 延迟 6 倍（单样本） | "一次性抖动，可能对方网络不稳" → `notice`，confidence 0.62 | 期望告警 |
| `aw_07` 结构变更 | "看起来是改了返回格式" → `notice`，confidence 0.75 | 期望告警 |

**它认出了根因，只是不肯为此叫醒你。** 这是**校准分歧**，不是能力缺陷 ——
甚至可能是我的标签太严（单样本 6 倍延迟，一个老练的运维确实会先观察）。

**但我没有改标签。** 看到模型答案之后再改题，就是把测试集往模型上拟合 ——
那种"改进"毫无意义。要改就得有**独立的判据**，比如先写下一条明确策略：

> p95 超过基线 3 倍、且**连续两轮**成立 → 告警；单轮 → notice。

然后用这条策略重标所有场景。那是一次真正的迭代，而不是事后调答案。

### 下一步（由这次结果驱动）

1. **补"证据不足"题型**：把 `run_doc` 里的 `baseline` 或历史**拿掉**，
   只留当前一轮 —— 这时"是新目标还是长期故障"在输入里无法区分，
   **必须**去查 `history`。这才是能体现工具价值的题型。
2. **先定阈值策略、再重标标签**（如上），让 `recall` 度量的是能力而不是"是否和我一样保守"。
3. **要主张成本差异，就得重复跑**（`--repeat 3`），单次 18% 不作数。

## 自检：一条命令回答"现在能不能正常工作"

这个项目里**真正花时间的从来不是写代码，而是排查"为什么它没动静"**：
SMTP 端口通不通、授权码抄全没有、判断层能不能写自己的 home、
工具预算能不能落盘、数据库迁移跑上没有、计划任务到底注册没注册。

这些我这次一遍一遍地查。所以固化成命令：

`heartbeat` 的配置在 `[schedule.heartbeat_expect]` 而不在 `[heartbeat]`（我列错了检查项），
以及 `check_golden_set()` 不接参数而 `run_doctor` 统一传 cfg。
两个都补了单测。

根因又是 `SMTP_SSL` 构造函数的隐式 EHLO 没填能力表 ——
和当初 `smtp_login()` 里踩的是同一个，修法也一样（显式补一次 `ehlo()`）。

## 小模型分流：让"需要多少判断"决定花多少钱

可用模型是 **`deepseek-flash`**（便宜）和 **`deepseek-v4-pro`**（强）——
用非法模型名触发的校验错误里列出来的（`dsh headless` 没有 `--model`，
所以走 patch 组合；后者覆盖前者，这一点用 `--dump-config` 验证过）。

分流判据的核心不是"异常多不多"，而是**"要不要在证据之间权衡"**：

| 类型 | 例子 | 模型 |
|---|---|---|
| 机械型 | 日志源不见了、心跳发现任务没跑、整轮采到 0 条 | 便宜（事实即结论） |
| 解释型 | 200 但内容变了、延迟涨 6 倍但只有单样本、冒出新错误模板 | 强（要权衡） |

外加：异常项 ≥ 2、失败目标 ≥ 2。**拿不准就升级** —— 分流的收益是成本，
代价是潜在准确率，所以先验宁可保守。

### 实测：三臂配对（19 场景，同一次运行）

| 指标 | flash（便宜） | v4-pro（强） | **自动分流** |
|---|---|---|---|
| `should_alert` 精确率 | 100.0% | 100.0% | **100.0%** |
| `should_alert` 召回率 | 90.9% | 100.0% | **100.0%** |
| `should_alert` 准确率 | 94.1% | 100.0% | **100.0%** |
| 严重级别准确率 | 100.0% | 100.0% | 100.0% |
| 根因关键词命中率 | 92.9% | 100.0% | 92.9% |
| **输入 tokens** | 133,349 | 150,403 | **99,817** |
| 输出 tokens | 98,538 | 152,051 | 120,679 |
| cache 读 | 1,321,344 | 995,072 | **930,176** |
| 平均耗时 | 31.6s | 80.6s | 55.5s |

**怎么读：**

1. **分流拿到了强模型的决策准确率**（精确率/召回率/准确率都是 100%，与 v4-pro 持平），
   而便宜模型是 94.1%/90.9%。
2. **代价只有强模型的 2/3 输入**（99,817 vs 150,403，**少 34%**），
   耗时也快 31%（55.5s vs 80.6s）。
3. **代价是根因命中率**：分流 92.9%，与便宜模型相同，比强模型低 1 个场景。
   所以正确的说法是"**几乎**拿到了强模型的效果"，不是"完全等价"。
4. 仍然是每臂单次采样。附录 H 已经证明单次分数会抖，
   **要坐实这个 34% 得加 `--repeat`。**

## 多视角诊断：让三个镜头各自说话

单次判断里，模型要在**同一次思考**中同时回答三个性质不同的问题
（对方行为变了吗 / 日志里有证据吗 / 这是新问题吗），它们会互相干扰 ——
模型容易抓住**最显眼**的那条线索就下结论。启用后它会**先并行派子代理分头查证，再汇总**。

配置默认 **关**（`[ai.multi_perspective] enabled = false`）—— 它把 token 消耗放大数倍，
不该默认开。评测里用 `--perspectives` 强制打开。

### 实测：它真的派了子代理

```
[call] subagent  契约镜头查证
[call] subagent  日志镜头查证
[call] subagent  历史镜头查证
[call] write     ← 汇总后写结论
```

耗时 59.4s（基线 27.8s），三个镜头并行、汇总后答对。

### 但它暴露了一个我自己写的 bug —— 而且是最有价值的那类

第一次跑通时，多视角臂**答错了**：

| | 结论 | 置信度 |
|---|---|---|
| 基线 | 结构变更，"是对方自己改了接口，不是我们这边的问题" | 0.82 → **告警** |
| 多视角 | "是谁改的、为什么改的，我们这边什么线索都查不到" | 0.70 → **撤回告警** |

三个镜头都如实回报"查不到线索"，汇总时模型把置信度降到 0.70 并**撤回了本该发的告警**。

**根因是概念混淆**：多镜头回答的是**"为什么"**，不是**"是不是问题"**。
三个镜头都查不到原因，**并不改变异常本身是否成立** —— 返回结构变了就是变了。

修法是在汇总指令里明确要求区分两类不确定：

> ⚠️ 汇总时必须区分**「原因不明」**和**「是否异常不明」**。
> 镜头查不到原因，**不改变异常本身是否成立**……`severity`/`should_alert`
> 依据的是**异常本身**，不是你能不能解释它。

修完重跑同一场景：**派出三个子代理且答对了**。

> ⚠️ **诚实说明**：修前修后各只跑了**一次**，而且这一臂的行为波动很大
> （三次运时分别 144.5s / 17.8s / 59.4s —— 有一次压根没派子代理）。
> 所以"修复有效"是**一次观察，不是结论**，要坐实得加 `--repeat`。

## 只读面板：把已有的东西摆到一起

```bash
python tools/dashboard.py              # http://127.0.0.1:8899/
python tools/dashboard.py --json       # 打印汇总 JSON
python tools/dashboard.py --once       # 渲染一次 HTML 到 stdout
```

首屏第一块是**"需要你注意的事"**（未恢复告警 + 自检失败项），空闲时明确写"没有"。
运维面板要回答的是"**有东西坏了吗**"，不是"欢迎使用运维平台"。

它显示：任务健康度（距今多久 vs 预期间隔）、未恢复告警、成本、告警统计、
人工反馈、评测分数、最近运行。

四条约束，每条都有理由：

| 约束 | 理由 |
|---|---|
| **零前端依赖**（内联样式单页） | 项目一路坚持零第三方依赖，面板不该是第一个例外 |
| **只绑 `127.0.0.1`** | 它读的是你的运维数据（含告警详情），不该出现在局域网上 |
| **只读**（全部查询走 `mode=ro`） | 一个能触发动作的面板就是一个新的攻击面 |
| **没有它也能用** | 报告是 markdown、数据在 SQLite、告警在邮件里；它不是新的真相来源 |

两个实现细节：**`eval` 与 `doctor` 两块不依赖历史库**，所以放在最前面算
（一台还没跑过任何任务的机器也该看到自检结果）；**HTML 必须转义** ——
面板渲染的是日志内容，而日志是**外部输入**，`<script>` 完全可能出现。

### 顺带补上的一个系统性缺口

写面板时我又踩了自己的老坑：忘了在最开头调 `make_console_safe()`，
于是 HTML 里的 `⚠️` 把 GBK 控制台打崩了。

项目一开始就为它做过根因修复、也留了测试 —— **但那个测试只覆盖 `python -m ops`，
没覆盖 `tools/` 下的脚本**。所以新脚本又踩了一遍。

于是补了一条**系统性**测试：用 AST 扫所有入口脚本，检查是否调用了它。
它上线立刻又抓出 **4 个**漏掉的脚本（包括会打印中文表格的 `eval_suite.py`）。

> **靠人记住"新脚本要加一行"是靠不住的；让测试去扫，才叫系统性。**

## 价格监控：同一套骨架，换一个场景

"东西坏了吗"和"现在该不该买"是两种问题。`price_watch` 用**同一套骨架**回答了后一种：

```bash
python tools/price_stub.py --port 8790          # 起本地演示价格源（不碰任何真实站点）
python -m ops --task price_watch --once --dry-run `
    --override price_watch.items.0.enabled=true
```

**复用了什么**（一行都没重写）：落库、基线、AI 归因、去重冷却、静默时段、
邮件通道、恢复通知、报告、只读调查工具、小模型分流、N 臂评测。

**只换了两块**：

| | 采集 | 判据 |
|---|---|---|
| `api_watch` | 探测接口是否活着 | 连续失败 / 延迟回归 / 结构变更 |
| `price_watch` | 按配置抓 JSON 里的价格字段 | 到价 / 单次涨跌幅 / 窗口新低 / 数据源静默 |

### 一个关键设计差别：价格**没有"正常值"**

所以这里刻意**不用**"偏离基线 N 倍" —— 那需要先假设价格有个基准，而它没有。
只用三个有明确含义的判据：**用户设的目标价**（唯一确定的）、
**相对上一次的变化幅度**、**窗口极值**。把它当 `api_watch` 调参，
结果只会在促销季疯狂误报。

另一个差别：**跌破目标价是好消息**。故障告警说"出事了"，价格告警说"可以买了"。
所以这些异常走 `notice` 级别，提示词里明确要求"语气是机会不是事故"，
冷却时间也建议给大（价格在目标价附近震荡时最烦人）。

### 采集为什么是配置驱动，而不是写死爬某个电商

那类页面有反爬、有 ToS 限制、改版就失效。**把系统绑在一个随时会坏的抓取上，
是这类项目最常见的死法。** 这里只提供"给定地址和取值方式就能用"的能力：

```toml
[[price_watch.items]]
name = "rtx5070"
url = "https://你的价格来源/api/item/5070"
price_path = "data.price"      # 支持 a.b.0.c
target_price = 4000            # 到价就叫我
drop_percent = 8               # 一次降 8% 也叫
new_low_days = 14              # 创 14 天新低
```

### ⚠️ 实测：有价格的站点**全都自动抓不到**

我拿真实目标（下面那个 DGX Spark）实测了一轮，结论不客气：

| 站点 | 结果 |
|---|---|
| NVIDIA 官方 store / marketplace | 超时、连接被断 |
| NVIDIA 商品页（美国/中国） | 200，但**页面里没有价格**（营销页，价格在 JS 里） |
| B&H Photo / Micro Center | **HTTP 403** |
| Newegg / CDW | DNS 解析失败 / 连接被拒 |
| 京东商品页 | 200，但只有 2.7KB —— **反爬页** |
| 什么值得买 / 慢慢买 | 同上，返回反爬页 |

**这不是"配置没写对"，是这类站点的常态。** 所以系统把"抓不到"当成
**一等公民**来处理，而不是当例外：

### 三种来源（写在一个商品块里就是它）

| `source` | 怎么取 | 适合什么 |
|---|---|---|
| `manual` | 人工录入，`tools/price_set.py --item X --price Y` | **抓不到的源 —— 最实用的形态** |
| `json` | `url` + `price_path` | 有 JSON 接口的源（比价服务、自己的中间层） |
| `html` | `url` + `price_regex` | 你能打开、但价格在 HTML 里的页面 |

`manual` 是**一等公民，不是补丁**：对"一个月看一次"的贵设备，
你本来就要去看价格，顺手记一条的成本是 5 秒 —— 而历史、判据、到价提醒、
涨跌提醒、告警邮件、报告、趋势**全部自动**。

**并且它不会假装自己在自动抓**：判断层拿到人工价格时，
会在结论里明说"这个价是人工录入的、不是抓来的，建议你向实际卖家复核"。

### ⚠️ 到价只报"刚跌破"，不报"一直在下面"

这是价格监控能不能用的**关键一条**，也是我在准备注册每日任务时才想清楚的：

> 价格一旦低于目标价，如果每轮都报，你会一天收到两次一模一样的消息，
> 然后就会把通知关掉 —— 那正是"告警系统死于误报"的标准死法。

所以判据是**跨越**（上次在目标价之上、这次不在），不是**状态**（现在在不在下面）。
持续在下方时会记一条说明（"仍在目标价之下，这是持续状态，不重复提醒"），
但**不打扰你**。先涨回去再跌破，会重新提醒 —— 那是新的一次机会。

有专门的单测锁住这条（`test_already_below_target_does_not_repeat`）。

### 京东实测：能自动抓，但**必须带你的登录 Cookie**

你说你一般去京东看价格，所以我把京东这条路完整走了一遍：

| 地址 | 结果 |
|---|---|
| `item.m.jd.com/product/<sku>.html`（移动版） | ✅ **可达**，275KB 真实页面，标题能确认是那个商品 |
| `item.jd.com/<sku>.html`（PC 版） | ❌ 2.7KB 反爬页 |
| `p.3.cn/prices/mgets`（京东自营价格接口） | ❌ 超时 |
| `c0.3.cn/stock`（库存价接口） | ❌ DNS 解析失败 |
| `item-soa.jd.com/getWareBusiness` | ❌ 返回 HTML，不是 JSON |

移动版页面里，价格这个字段长这样：

```json
"priceFloor": {"demoteEnable":false,"price":"4??00","type":"251", ...}
"priceFloor":{"priceLoginText":"登录查看价格"}
```

那几个 `?` 是**真的问号字符**（0x3F）—— 京东对**未登录**请求返回的是
**掩码占位价**。所以结论确定：**京东要登录才给价格**，不是反爬也不是配置问题。

**⚠️ 先记住一件事：不要用控制台 `copy(document.cookie)` 取 Cookie。**

这个坑我实测踩过，而且很隐蔽：

| | |
|---|---|
| 现象 | 那句命令**成功返回 `undefined`**，你剪贴板里也确实有东西 |
| 真相 | 拿到的是一串**无关的跟踪 Cookie**（`__jdv`、`shshshfpa`…），**没有登录凭证** |
| 原因 | 京东的 `pt_key` / `pt_pin` 是 **HttpOnly** —— 浏览器**故意不给网页脚本看** |
| 后果 | 你以为拿到了，配进去，页面照样说"需要登录" |

而且京东风控通常还需要 `wlfstk_smdl`、`sdtoken` 这些，
所以"只挑 pt_key + pt_pin 两个"也不一定够。**要拿就拿完整的。**

**✅ 正确做法：让浏览器自己导出整个请求（两步）**

```bash
# 第 1 步（浏览器里）：让浏览器把整个请求交出来
#   1) 京东页面右键 → 「检查」
#   2) 点顶部「网络」标签，按 Ctrl+R 刷新页面
#   3) 左边列表里右键最上面那条请求（通常是 .html 或 doc）
#      → 「复制」→「以 cURL 格式复制 (bash)」

# 第 2 步（终端里）：它自动读剪贴板、提取 Cookie、写进密钥文件
python tools\import_cookie.py
```

为什么这条路能拿到 HttpOnly Cookie：**"复制为 cURL"是浏览器导出它
实际发出去的那个请求**，包含全部请求头 —— 包括它自己藏起来不给脚本看的那些。

工具会把"提取"这一步做掉（那串 cURL 很长，人手工挑 Cookie 极易挑错），
并且**只报告 Cookie 的名字、不打印值**，所以你截图求助也不会泄露凭据：

```
找到 Cookie：1380 字符，12 个 Cookie：__jdv, pt_key, pt_pin, wlfstk_smdl, …
已写入 D:\AITool\ops-pipeline\config\secrets.local.toml
  OPS_JD_COOKIE          __jdv=76…defg
```

如果传进去的其实是控制台那种"缺 pt_key"的 Cookie，它会**提醒但不拦你**。

> ### ⚠️ 一条我自己被推翻的判断（值得记下来）
>
> 我一开始认为"没有 `pt_key` 就一定不行"，还把它写成了强警告。
> **实测证明我错了**：用户导入的那串**没有 `pt_key`**（只有风控 token），
> 京东商品页**照样返回了真实价格**。
>
> 也就是说，京东商品页那道闸主要是**风控校验**
> （`wlfstk_smdl` / `sdtoken` / `shshshfpa` 这些），`pt_key` 反而不是必需的。
>
> **教训：过度警告和没有警告一样有害。** 它会让用户以为"白做了"而放弃 ——
> 正确的做法是提示"先试一下，别在这里下结论"。

### ⚠️ 这轮实测抓到的两个"看起来能跑但结果是错的"陷阱

比抓不到更糟的是**抓到错的**——抓不到会报警、有人会去看；
抓到错的会安静地产生假历史、假新低、假跌幅，把整个价格库污染掉。
这轮踩到两个，都补了守卫和回归测试：

**① 宽松正则匹配到页面上无关的数字。** `"price"\s*:\s*"?([0-9][0-9,]*)"?`
在京东页面上匹配到了 `"price":"4??00"`，捕获出 `4` —— 系统会把 **¥4**
记成这台三万块设备的价格，下一步就是"暴跌 99.99%"。

**② 剥掉掩码字符会凭噪声捏造一个价格。** 就算正则抓对了整个 `4??00`，
`parse_price` 会把 `?` 当噪声剥掉，于是 **`4??00` → 400**。
一个完全由噪声捏造出来的数字，比"解析失败"危险得多。

两道守卫：

```toml
# ① 掩码字符一律判为解析失败（写在代码里，不需要配置）
# ② 合理性区间 —— **自动抓时必须设**
min_price = 15000
max_price = 80000
```

区间外的值一律当**解析失败**处理，而不是当价格。

### 接这个场景时抓到的两个真 bug

**① 本轮样本污染了"上一次价格"** —— 本轮的样本在统计之前就落库了
（和 `api_watch` 一样），于是"上次价格"就是**本轮自己**，
`(现价 - 上次价)` 恒等于 0，**`price_drop` 永远不会触发**。
不报错、不变慢，只是安静地什么都不做。

它当初"看起来能用"，是因为两次运行落在同一秒、`ts` 精度只有秒，
SQLite 恰好返回了另一行 —— **是运气，不是设计**。修法是把本轮 `run_id` 排除掉。

> 对照：`api_watch` **故意**包含本轮 —— "这是第 3 次连续失败"本来就该算上当前这次。
> **同一个表，两个场景要的基线不一样。**

**② `JsonResponse.ok` 的含义是"有响应"，不是"成功取到"** ——
它的设计目的是给契约断言层用（4xx/5xx 也算有响应、也要能看到状态码）。
价格采集拿它判断就会把一个 404 的响应体当成有效数据继续往下走。

两个 bug 都补了回归测试。

## 已知限制

- **巡检会话用新会话**：`api_watch` 每小时独立判断，不累积记忆。
  固定会话（有记忆）留给需要跨天对照的日报类任务 —— 这是刻意的，不是遗漏。
- **单机设计**：没有并发抓取、没有分布式，个人规模不需要。
- **公开 API 要礼貌**：默认 `concurrency` 顺序执行 + `rate_limit_ms`，只监控你有权调用的接口。
- **日志模板会折叠变量**：`status=200` 与 `status=500` 归进同一个模板（数字被泛化）。
  严重性靠**日志级别**判断，不靠模板里的状态码 —— 这是模板聚类的固有取舍，不是缺陷。
- **两个窗口需要 2×window_hours 的日志**：日志轮转太快（例如只留 12 小时）会让基线窗口为空，
  此时会退到历史基线或标记冷启动。

## 扩展一条新流水线

1. `ops/tasks/` 加一个模块，导出 `run(cfg, *, dry_run, no_ai) -> int`
2. `ops/__main__.py` 的 `TASKS` 字典里注册
3. `ops/prompts/` 加提示词 —— 关键是交代清楚**哪些是事实、哪些要你判断**
4. `config/config.toml` 加配置段；`[schedule.heartbeat_expect]` 加一条期望间隔
5. `scripts/register_tasks.ps1` 加一个触发器

`core/` 里的能力（存储、判定、告警、报告、AI 桥、收尾流水线）直接复用，不用重写。
`api_watch`、`regression`、`log_scan` 是三个可参考的完整例子 ——
它们分别代表"探测外部依赖"、"跑自己的用例"、"分析非结构化数据"三类形态。
